# 第七章 互联网中 QUIC 协议潜在漏洞威胁测量

## 7.1 研究目标与核心问题

前文已经在主流 QUIC 实现中发现并确认了多类真实的逻辑漏洞。然而，实验室环境中的漏洞触发结果只能说明相关缺陷在特定实现中客观存在，还不足以直接说明其在真实互联网中的风险规模。对于互联网中的真实部署而言，漏洞是否会转化为可观测的安全暴露，除了取决于实现本身是否受影响，还与部署规模、接入方式、域名与证书配置、SNI 与 ALPN 要求、CDN 或云服务商的前置层策略，以及负载均衡与连接分流机制等因素密切相关。若缺乏部署侧信息，仅凭实验室中的复现结果，很难判断某类缺陷在真实网络环境中的实际危害范围。

基于这一认识，本章的研究目标是：在伦理可接受、交互影响可控的前提下，对当前互联网中 QUIC 服务的实际部署情况与潜在风险暴露情况进行系统测量。与前文侧重漏洞发现不同，本章更关注三个层面的问题：互联网中究竟存在多少对外暴露的 QUIC 服务；这些服务大致采用哪些实现，以及不同实现是否呈现明显的部署集中；在不突破最小影响边界的情况下，有多少目标表现出与已知逻辑漏洞模式一致的潜在威胁信号。

围绕这一目标，本文主要回答以下三个研究问题。

RQ1：互联网中存在多少对外暴露的 QUIC 服务，其全网规模大致如何。

RQ2：这些服务分别采用哪些 QUIC 开源实现或实现簇，不同实现的部署分布是否呈现明显的集中现象。

RQ3：在伦理可接受、低影响的探测边界内，有多少目标表现出与已知逻辑漏洞模式一致的潜在威胁信号，这些信号主要集中在哪些实现和部署中。

为回答上述问题，本文设计并实现了一套面向真实互联网环境的自动化测量流程。该流程由四个阶段组成。第一阶段通过全网版本协商探测识别可能支持 QUIC 的目标，并提取其初步协议特征；第二阶段在与奇安信的合作基础上，利用被动 DNS 数据对这些目标执行域名反查，生成候选域名集合；第三阶段基于候选域名进行 SNI 连通性验证，并进一步提取实现识别所需的附加信号；第四阶段仅在已经确认可完成最小握手的目标上执行低影响漏洞探针，对风险信号进行分级、聚合与输出。通过这种分层设计，可以将“发现”“关联”“验证”“探测”四类证据相互区分，从而在相对独立的证据链基础上回答不同研究问题。

本章的测量严格遵循最小影响原则。首先，在全网发现阶段优先采用短交互、低状态的 QUIC 探针，不直接进入完整业务会话。其次，在连通性验证阶段，一旦确认握手能够建立，系统立即发送 `CONNECTION_CLOSE` 并结束交互，不保持长连接，也不交换额外应用数据。再次，在风险探测阶段，本文针对所有漏洞模式都设计了受限规模的最小化探针，使其交互长度和状态影响均被压缩到较低水平。换言之，本章的目标不是对互联网目标实施完整利用，而是在尽量不干扰真实业务的前提下，识别与已知漏洞模式一致的潜在风险信号。

## 7.2 全网 QUIC 服务发现与实现识别

### 7.2.1 基于 ZMap 与版本协商的数据探测

全网 QUIC 服务发现的首要难点在于，QUIC 作为基于 UDP 的协议，并不存在类似 TCP 三次握手那样统一而稳定的“探测起点”。若探针缺乏足够的协议形状，许多实现不会将其视为合法的 QUIC 初始报文；但若直接进入完整握手，又会在大规模扫描中引入不必要的状态开销。基于这一矛盾，本章在发现阶段采用参考 QUIC Hunter 工作的 `Initial-VN` 思路，即发送一个形态完整的 QUIC Initial 探针，但将其中的版本字段设置为保留版本号，以期在维持低状态探测的同时获得更高的发现率。

这一设计的关键动机在于，不同 QUIC 实现对初始报文的解析顺序并不完全一致。对于一类实现而言，只要版本字段不被支持，便会立即返回 Version Negotiation；但对另一类实现而言，版本检查并不是最先发生的步骤，它们往往会先尝试解析 Initial 报文的基本结构，再决定是否返回协商结果。若探针仅包含一个不完整的保留版本号载荷，而缺乏合法 Initial 的基本形状，那么这些实现便可能直接丢弃探针，从而在全网发现阶段被系统性漏检。采用“合法 Initial 形状 + 保留版本号”的探针，正是为了降低这类实现差异对发现结果的影响。

在具体判定上，本文将两个条件都视为 QUIC 可达证据。其一，若目标返回标准的 Version Negotiation，则提取其中宣告的版本集合，并将其作为后续协议特征分析的基础；其二，若目标未返回 Version Negotiation，而是返回了与探针版本一致的 Long Header 响应，则说明该目标至少已经接受并处理了合法 Initial 的基本结构，同样可将其视为 QUIC 服务的可达证据。为了避免普通 UDP 噪声或其他协议回包被误识别为 QUIC，本章在解析过程中进一步校验连接 ID 的对应关系，仅在目标连接 ID 与原始探针源连接 ID 之间满足一致性约束时，才将其纳入后续分析。

通过这一策略，第一阶段的结果不再只是一个“能否解析出版本列表”的二元集合，而是形成了更细粒度的发现证据。对于返回 Version Negotiation 的目标，可以得到其支持版本集合；对于只返回合法 Long Header 的目标，则至少能够确认其具备 QUIC 层响应能力。前者为实现识别提供了直接线索，后者则保证这些目标不会因为实现差异而在第一阶段被过早排除。

### 7.2.2 基于 PDNS 的域名猜测与部署关联

完成第一阶段之后，系统得到的是一个“可能支持 QUIC 的目标 IP 集合”。但在真实互联网中，IP 地址本身往往不足以直接建立有效的 QUIC 会话，尤其是在 CDN、多租户云服务和前置代理广泛存在的场景下，缺失正确的域名上下文通常会导致握手失败、返回泛化错误，甚至直接超时。因此，在进入状态化验证之前，有必要为每个候选 IP 构造尽可能合理的域名候选集合。

为此，本文在第二阶段引入基于被动 DNS 的域名反查。通过与奇安信合作，系统对第一阶段得到的目标执行被动 DNS 反查，并按时间窗口区分当前域名与历史域名，形成面向后续握手验证的候选集合。这里需要强调的是，这一步的目的并不是证明漏洞，也不是直接推断服务实现，而是为第三阶段的 SNI 连通性验证提供更接近真实部署语境的上下文信息。

从测量方法上看，被动 DNS 反查具有两个作用。第一，它将“裸 IP 发现”转化为“IP 与域名候选集合”的关联结果，从而提高后续握手能够成功建立的概率。第二，它为部署分析提供了额外的组织与业务上下文，使后续结果不仅能够按 IP 聚合，也能够按域名和所属组织进行归并。对于使用多域名共享同一边缘接入点的目标，这一步尤为关键，因为许多表面上“不可达”的目标并非不支持 QUIC，而只是缺少正确的 SNI。

当然，被动 DNS 反查并不能覆盖所有场景。一些目标可能依赖私有域名、短生命周期域名、专用接入参数或仅在特定业务路径上开放 QUIC，这些都可能使候选域名集合仍然不完整。但与直接对裸 IP 做状态化探测相比，PDNS 反查至少提供了一种更接近真实部署上下文的连接入口，从而降低因域名缺失带来的系统性漏检。

### 7.2.3 多指标冗余实现识别与投票判定

在完成服务发现与域名关联之后，下一步需要回答的是这些部署背后究竟采用了哪些 QUIC 实现。仅依赖单一指纹往往难以得到稳定结论。一方面，版本协商暴露的版本序列具有一定区分度，但不同实现之间可能出现重叠；另一方面，许多真实部署会经过前置层封装、实现分叉或局部修改，使得某一类单独特征不足以支撑稳健判定。基于这一考虑，本文不采用单一指纹直接分类，而是构造一个由多类弱证据组成的冗余识别框架，并通过投票方式给出实现候选。

第一类证据来自版本协商阶段暴露的版本序列特征。对于返回 Version Negotiation 的目标，服务器宣告的版本集合与排列方式往往具有一定实现差异，可作为快速初筛依据。这类证据获取成本低、覆盖面广，适合在大规模测量中首先使用，但其区分能力有限，因此在本章中只承担初筛作用，而不直接作为最终实现标签。

第二类证据来自握手失败路径上的 `CONNECTION_CLOSE`。参考 QUIC Hunter 的识别思路，本文对已经获得 SNI 上下文的目标额外构造 `ALPN=invalid` 的最小化握手请求。不同实现在遇到非法 ALPN 时，往往会返回风格不同的错误码、错误消息或关闭语义。尽管这些差异不能保证对所有实现都唯一，但它们具有一个重要优势：即使握手没有成功完成，也可以从关闭路径中获得可用于识别的信号。因此，这类证据特别适合用于补充那些无法进入成功握手、却仍有明确 QUIC 响应的目标。

第三类证据来自成功握手后的 TLS 扩展顺序与 QUIC transport parameter 顺序。对于能够完成最小握手的目标，服务器在握手过程中暴露的参数排列方式通常比版本序列更细致，也更接近实现层行为。尤其是 transport parameter 的发送顺序，常常与具体实现内部的编码逻辑有关，因此在多实现区分中具有较高价值。当然，这类证据也存在限制，例如部分实现可能随机化顺序，或由于前置层与开源实现之间存在改造而呈现混合特征。因此，本章并不把它视为绝对标签，而是把它作为高权重证据纳入投票框架。

在最终判定时，系统将上述三类信号分别编码为版本特征、错误消息特征和顺序特征，并对它们进行联合投票。若多类证据指向同一实现，则将该结果视为较强候选；若不同信号之间存在冲突，则保留冲突说明，并根据证据强弱将其降级为实现簇或低置信候选。这样做的目的，不是追求对每一个目标都给出看似精确的唯一标签，而是尽可能在全网尺度上获得稳定、可解释的实现分布估计。换言之，本章所强调的是“基于多源弱证据汇聚的实现识别”，而不是“依赖单一指纹的确定性分类”。

## 7.3 潜在漏洞威胁探测方案

### 7.3.1 基于已知漏洞模式的轻量探针设计

在前述阶段之后，系统已经能够从全网范围内筛选出具备 QUIC 可达性、且能够在给定 SNI 条件下完成最小握手的目标。本章的最后一个核心问题，是在这些目标中识别与前文已知漏洞模式一致的潜在风险信号。与前文的漏洞发现工作不同，这一阶段不再追求触发实现内部尽可能复杂的状态空间，而是强调探针的轻量化、交互的可控性与结果的可解释性。

因此，本章的风险探针设计继承前文已确认的漏洞模式，但在互联网测量场景下进行了严格约束。具体而言，每一类探针都被压缩为受限规模的短序列，只保留对漏洞模式最关键的触发条件，避免无关状态扩张和长时间连接维持。探针的观测目标也被重新定义为“是否出现与已知漏洞模式一致的异常响应”，而不是“是否在远端完全复现实验室中的利用结果”。这种调整使得风险探测从“漏洞利用导向”转变为“风险信号识别导向”，更符合互联网测量的伦理边界。

在判定逻辑上，本章不把任何一次异常响应直接等同于已确认漏洞，而是将其视为风险证据的一部分。只有当一个目标在轻量探针下表现出与已知漏洞模式一致、且具有重复解释基础的响应特征时，系统才将其记录为潜在威胁信号。通过这种方式，可以在尽量降低交互强度的同时，保留对大规模真实部署进行安全观察的能力。

### 7.3.2 以 CRYPTO FLOOD 为例的模糊探测方法

为了说明上述设计思想，本节以 CRYPTO FLOOD 类问题为例，说明本章如何将实验室中的漏洞模式转化为互联网场景下的轻量探针。对于这类问题，前文已经表明，其关键不在于单个报文是否合法，而在于受测实现面对受限但持续的特定帧序列时，是否会表现出异常的资源消耗倾向、非预期的连接状态推进，或者与常规实现明显不同的关闭行为。

在互联网测量中，本文并不复制实验室中更长、更激进的触发序列，而是提取其中最核心的结构特征，构造一个更短的模糊探针。这里所谓“模糊”，并不是指完全开放式的模糊测试，而是指在已知漏洞模式附近保留少量结构扰动，使探针既能覆盖该模式的关键行为区间，又不会演化为高强度的利用负载。对于 CRYPTO FLOOD 而言，这样的探针通常表现为受限数量的关键帧组合，以及围绕这些帧的少量顺序与负载扰动。

这一方法的意义在于，它把原本依赖本地重放和长交互的漏洞模式，转化为可在互联网环境中执行的短交互风险探针。若目标在这样的轻量化探针下仍然表现出与已知问题一致的异常响应，则说明该风险模式并非只存在于实验室构造环境中，而有可能已经进入真实部署。反之，即使某一实现在理论上受影响，但若真实互联网中的部署没有呈现相应信号，也说明部署侧条件可能对其形成了事实缓解。

### 7.3.3 风险证据分级与结果输出

由于互联网测量中的异常响应可能受到网络抖动、前置层策略、重传行为以及瞬时负载等因素影响，本章对风险结果采用分级输出，而不使用简单的“有漏洞”或“无漏洞”二元标签。更具体地说，系统首先为每一次探针交互保留原始观测结果，包括连接状态变化、关闭行为、关键帧响应以及与期望模式的偏离方式；然后再在更高层面上将这些观测整理为风险证据。

风险证据的整理遵循两个原则。其一，单个目标的单次响应不直接解释为已确认漏洞，而是作为该目标的一条潜在线索。其二，分析输出优先在更高层级上进行聚合，包括 IP、域名与所属组织三个维度。这样做的原因在于，互联网中的大量地址往往并非独立部署，而是同一组织、同一平台或同一实现簇下的重复暴露。若只按 IP 做简单统计，容易夸大部署规模，也不利于刻画风险在实现和组织层面的集中情况。

因此，本章最终输出的不是“某个地址一定存在某个漏洞”，而是“某个地址或某个部署集合表现出与某类已知漏洞模式一致的潜在威胁信号”。这种表述一方面保留了对真实风险的敏感性，另一方面也避免了在缺少人工验证和责任披露环节的情况下，对互联网目标给出过于强的确定性判断。

## 7.4 结果分析框架与局限

本章的结果分析围绕前三个研究问题展开，并分别对应三类统计视角。对于 RQ1，应重点描述全网 QUIC 服务发现结果，包括可达地址规模、组织分布与不同扫描条件下的发现差异；对于 RQ2，应重点分析实现候选的总体分布、主要实现的集中程度，以及版本特征、错误消息特征与顺序特征之间的一致性与冲突情况；对于 RQ3，则应重点呈现风险信号在实现、域名与组织层面的聚合结果，并讨论哪些实现簇和部署场景更容易出现与已知漏洞模式一致的异常响应。通过这三类视角，可以把“服务规模”“实现分布”和“风险暴露”置于同一分析框架之下，而不是彼此割裂地讨论。

尽管如此，本章的方法仍然存在若干不可避免的局限。首先，在发现层面上，隐藏 SNI、专用 ALPN、私有接入策略以及仅对特定业务路径开放的 QUIC 服务，都可能导致目标在测量中被漏检。即使采用了合法 Initial 形状与被动 DNS 辅助，仍无法保证覆盖所有真实部署。其次，在识别层面上，开源实现的分叉、自定义补丁、CDN 前置层和代理链路都可能改变外部可见的协议特征，从而稀释开源库原始指纹的辨识能力。因此，本章给出的实现标签更适合被理解为“实现候选”或“实现簇归属”，而不是对真实代码库来源的绝对判定。

最后，在风险层面上，本章采用的是轻量探针与风险信号识别方法，其输出本质上是“潜在威胁证据”，而不是严格意义上的已确认漏洞。一个目标表现出与已知模式一致的异常响应，说明其存在值得进一步关注的风险，但并不等同于已经完成了充分复现、人工验证与责任披露。也正因为如此，本章在结论上强调的是潜在风险暴露规模，而不是已确认漏洞实例数量。这样的界定虽然较为克制，却更符合互联网安全测量的伦理要求，也更有助于将前文的漏洞发现工作与真实部署环境中的风险评估合理衔接起来。

### 7.4.3 局限性

本章的方法仍有三个方面的局限。

第一，发现偏差仍然存在。隐藏 SNI、专用 ALPN、私有接入策略以及只对特定业务路径开放的 QUIC 服务，都可能导致目标在测量中被漏掉。即便采用了合法 Initial 形状和被动 DNS 辅助，也无法保证覆盖所有真实部署。

第二，识别偏差不可完全避免。开源实现的分叉、自定义补丁、CDN 前置层以及代理链路都可能改变外部可见的协议特征。因此，本章给出的实现结果应理解为外部观测条件下的实现候选，而不是对目标真实代码来源的绝对判定。

第三，风险结论是有限度的。本文采用轻量探针识别潜在威胁信号，这些结果可以说明某一目标或某一部署集合与已知漏洞模式具有一致的外部表现，但不能替代人工复现、深入验证和责任披露。基于这一考虑，本文在结论中讨论的是潜在风险暴露，而不是已确认互联网漏洞实例。
